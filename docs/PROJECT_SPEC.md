# 個人知識筆記管理網站｜專案規格書

> 專案代號：NoteWeave（暫定，可再更名）  
> 文件用途：提供給 Claude Code、Codex 或其他 AI 開發代理，作為網站規劃與實作依據。  
> 部署目標：GitHub Pages（第一階段以純前端靜態網站為主）。

---

## 1. 專案願景

建立一個以 Markdown 為核心的個人筆記與知識管理網站。使用者可以收集課堂筆記、閱讀摘要、研究資料、想法與各類文件，再透過分類、標籤、雙向連結及知識整理，逐步形成一套可持續累積的個人知識庫。

本網站不是單純的線上記事本，也不應只是把檔案丟進資料夾。核心價值是：

1. **保存原始資料**：保留使用者輸入或匯入的原始筆記，不因整理而覆寫原文。
2. **整理成知識**：將多篇相關筆記整合成主題文章，補充脈絡與關聯。
3. **建立知識連結**：讓筆記、主題、概念與來源彼此連結。
4. **方便查找**：透過全文搜尋、標籤、分類、索引及反向連結找到內容。
5. **資料可攜**：以 Markdown 作為主要資料格式，支援匯入、匯出及 Git 版本管理。

### 1.1 設計原則

- Markdown-first：內容以 Markdown 儲存與匯出，不綁定單一平台。
- Local-first：第一階段優先在使用者瀏覽器本機保存資料。
- Source-preserving：原始筆記與整理後文章分開管理。
- Human-in-the-loop：AI 提供整理建議，使用者確認後才套用。
- Progressive enhancement：先完成不依賴 AI 的核心功能，再逐步加入 AI。
- No fake features：所有畫面上的操作都必須有實際功能；未實作功能應標示為規劃中，不可用假資料假裝已完成。

## 2. 目標使用者與使用情境

### 2.1 目標使用者

需要長期累積課堂筆記、專題資料、技術知識、閱讀摘要或個人研究內容的學生及一般使用者。

### 2.2 主要使用情境

- 課後將老師講義、課堂重點或自己的理解整理成筆記。
- 匯入既有 Markdown 檔案，集中管理分散的筆記。
- 透過標籤與分類整理不同科目、專案或主題。
- 將多篇零散筆記整合成一篇完整的主題知識文章。
- 查詢某個概念，並查看相關筆記及來源。
- 定期檢查重複筆記、未分類內容及缺少連結的文章。
- 將整個知識庫匯出，保存在自己的電腦或 GitHub Repository。

## 3. 核心概念與資料分層

網站採用三層知識架構，並將整理流程與資料保存分開。

### 3.1 原始資料（Sources）

保存使用者最初提供的資料，例如：

- 手動建立的筆記
- Markdown、TXT 文件
- 課堂摘要、閱讀紀錄
- 網頁連結與參考資料
- 其他未來支援的文件格式

規則：

- 原始內容不可因 AI 整理而被直接覆寫。
- 每筆資料應保留建立時間、更新時間及來源資訊。
- 匯入相同檔案時應提供重複檢查，避免無提示地產生大量副本。

### 3.2 原始筆記（Raw Notes）

原始筆記是使用者可直接閱讀、編輯及管理的內容。

每篇筆記應包含：

- 標題
- 正文（Markdown）
- 分類
- 標籤
- 建立日期
- 最後修改日期
- 來源類型
- 相關筆記

### 3.3 知識庫（Knowledge Wiki）

知識庫是從多篇原始筆記整理而成的主題文章，例如：

- 「資料庫正規化」：整合不同課堂筆記中的正規化概念。
- 「機器學習」：整合模型、演算法、應用及相關案例。
- 「專題開發紀錄」：整合需求、架構、問題與決策。

知識文章應：

- 以主題或概念組織內容，而不是單純依日期堆疊。
- 保留引用來源，讓使用者能回到原始筆記。
- 使用內部連結連接相關文章。
- 標示資訊不足、內容衝突或尚待確認的地方。
- 允許使用者手動修正及維護。

### 3.4 三層關係

```text
使用者匯入／建立資料
          |
          v
    Sources 原始來源
          |
          v
    Raw Notes 原始筆記
          |
          | 使用者整理／AI 協助吸收
          v
    Knowledge Wiki 知識文章
          |
          v
    Index 索引、標籤、反向連結
```

原始來源、原始筆記與知識文章必須能夠分別管理，不可將三者混成同一種資料。

## 4. 網站功能需求

### 4.1 首頁 Dashboard

首頁提供知識庫概況及常用操作。

應包含：

- 全部筆記數量
- 知識文章數量
- 分類數量
- 標籤數量
- 最近編輯的筆記
- 最近新增的筆記
- 最近整理的知識文章
- 快速新增筆記入口
- 待整理項目，例如未分類筆記或未連結文章

數量必須從實際資料計算，不可寫死。

### 4.2 筆記管理

功能：

- 新增、檢視、編輯、刪除筆記
- Markdown 編輯器
- Markdown 即時預覽
- 自動儲存草稿
- 分類與標籤管理
- 建立日期、修改日期
- 釘選重要筆記
- 搜尋筆記標題與內文
- 依日期、標題、修改時間排序
- 匯入 Markdown 檔案
- 匯出單篇 Markdown 檔案

編輯器建議提供：

- 標題輸入區
- Markdown 工具列
- 編輯／預覽切換
- 字數統計
- 儲存狀態
- 標籤與分類設定

刪除前必須要求確認。自動儲存時應避免因快速切換頁面而遺失尚未完成的內容。

### 4.3 分類與標籤

分類（Category）採階層式管理，例如：

```text
學習
├── 程式設計
│   ├── Python
│   └── JavaScript
├── 資料庫
└── 人工智慧

專題
├── 系統分析
└── 系統開發

閱讀
└── 文章摘要
```

標籤（Tags）採多對多方式，一篇筆記可以有多個標籤。

分類與標籤的差異：

- 分類：決定筆記主要放在哪個知識區域。
- 標籤：描述筆記涉及的主題、用途或狀態。

### 4.4 知識庫 Wiki

功能：

- 建立知識文章
- 編輯及刪除知識文章
- 顯示文章引用的原始筆記
- 顯示相關知識文章
- 支援 `[[文章名稱]]` 內部連結
- 顯示反向連結（Backlinks）
- 顯示尚未建立目標文章的失效連結
- 依主題瀏覽文章
- 顯示文章建立及更新時間

知識文章與原始筆記必須有明確的類型區別。

### 4.5 知識整理（Absorb）

提供將多篇原始筆記整理成知識文章的流程。

第一階段可先提供人工整理模式：

1. 使用者選取一篇或多篇筆記。
2. 系統顯示選取筆記及內容。
3. 使用者建立新的知識文章，或選擇既有文章。
4. 系統提供來源清單及引用連結。
5. 使用者確認後儲存。

未來加入 AI 後，才擴充為：

1. AI 閱讀選取的原始筆記。
2. 找出核心概念、重點及彼此關聯。
3. 判斷應更新既有文章或建立新文章。
4. 產生整理草稿及來源引用。
5. 使用者檢查差異並確認。
6. 系統更新知識文章、索引及操作紀錄。

重要規則：

- AI 不可未經確認就覆寫原始筆記。
- AI 產生的內容必須能追溯來源。
- 不確定或互相矛盾的資訊必須標示，不可自行補成確定事實。
- 不可只為了增加文章數量而建立沒有實質內容的文章。

### 4.6 搜尋與查詢

第一階段提供本機搜尋：

- 搜尋筆記標題
- 搜尋筆記正文
- 搜尋知識文章
- 依分類篩選
- 依標籤篩選
- 顯示符合關鍵字的內容摘要

未來可擴充：

- 自然語言問答
- 跨多篇文章的知識整合
- 回答附上引用文章及原始筆記
- 找出知識庫尚未涵蓋的問題

查詢結果必須區分「資料中明確記載」與「根據資料推導」，資料不足時應明確說明。

### 4.7 知識庫檢查（Cleanup）

提供知識庫健康檢查：

- 未分類筆記
- 沒有任何內部連結的文章
- 失效的內部連結
- 疑似重複的筆記
- 缺少標題或必要 metadata 的文章
- 內容過長、可能需要拆分的文章
- 可能存在資訊衝突的文章

第一階段以規則檢查為主；AI 語意判斷列為後續擴充。

### 4.8 索引與活動紀錄

`_index.md`：

- 列出所有知識文章
- 依分類整理
- 提供文章簡介
- 記錄別名（aliases）
- 作為知識庫的主要導覽入口

`log.md`：

- 記錄新增筆記
- 記錄修改文章
- 記錄匯入及匯出
- 記錄知識整理操作
- 記錄知識庫檢查結果

操作紀錄應依時間排序，避免直接覆蓋舊紀錄。

## 6. UI／UX 設計規範

### 6.1 整體風格

採用簡潔、安靜、具有專業感的知識管理 SaaS 風格。

設計方向：

- 以淺色背景為預設。
- 使用低飽和度藍色或藍紫色作為主色。
- 以灰階建立資訊層次。
- 卡片及面板使用細邊框、適度圓角。
- 保持充足留白，避免畫面過度擁擠。
- 以排版與資訊層級為主，不使用大量裝飾插圖。
- 支援深色模式可列為後續功能。

### 6.2 操作體驗

- 常用功能應在一至兩次操作內到達。
- 新增筆記入口應容易找到。
- 搜尋應能快速開啟。
- 編輯及預覽切換必須清楚。
- 儲存狀態應明確顯示，例如「儲存中」、「已儲存」。
- 空資料時應顯示引導操作，不應只留白。
- 刪除、清空或匯入覆蓋等高風險操作必須二次確認。
- 手機版側邊欄應可收合。

### 6.3 響應式設計

至少支援：

- 桌面：主要開發與編輯環境。
- 平板：側邊欄可收合。
- 手機：單欄閱讀與編輯介面。

## 7. 技術架構與 GitHub 部署

### 7.1 部署前提

第一階段目標是部署至 GitHub Pages，因此網站必須能以靜態檔案方式執行。

建議技術：

| 層級 | 技術建議 |
|---|---|
| 前端框架 | React |
| 開發語言 | TypeScript |
| 建置工具 | Vite |
| 樣式 | Tailwind CSS |
| Markdown 編輯 | 支援 Markdown 的編輯器套件 |
| Markdown 顯示 | Markdown parser + 安全 HTML sanitizer |
| 本機資料庫 | IndexedDB |
| 搜尋 | 第一階段使用本機全文搜尋 |
| 版本管理 | Git / GitHub |
| 部署 | GitHub Pages + GitHub Actions |

可依開發實際情況調整套件，但應維持靜態部署相容性。

### 7.2 資料儲存策略

GitHub Pages 只負責提供網站靜態檔案，不會自動提供資料庫或後端 API。

第一階段建議：

- 使用 IndexedDB 儲存筆記及知識文章。
- 使用瀏覽器本機儲存使用者偏好設定。
- 提供 Markdown 匯入及匯出。
- 提供完整資料備份及還原。
- 清楚告知使用者：清除瀏覽器資料或更換裝置可能造成資料無法直接同步，因此必須定期備份。

重要限制：

- IndexedDB 資料不會自動同步到 GitHub Repository。
- GitHub Pages 不適合直接存放使用者私人筆記。
- 不可將 API Key 寫在前端程式碼或公開 Repository。
- 若未來要跨裝置同步、多人使用或安全地呼叫 AI API，應增加後端服務及資料庫，或採用經過安全設計的外部服務。

### 7.3 未來 AI 架構

AI 功能採模組化設計，第一階段不要求一定要連接付費 API。

未來可透過後端 API 或本機模型提供：

- 筆記摘要
- 重點擷取
- 主題分類建議
- 相關文章推薦
- 多篇筆記整合
- 知識問答
- 衝突及重複內容檢查

安全要求：

- API Key 只能存放於後端環境變數。
- 前端不得直接暴露正式 API Key。
- AI 生成結果先進入草稿／預覽狀態。
- 使用者確認後才寫入知識庫。

## 8. Markdown 檔案格式

所有筆記與知識文章都應使用一致的 YAML Frontmatter。

### 8.1 原始筆記範例

```markdown
---
id: note-20261116-001
title: 資料庫正規化
type: note
category: 資料庫
tags:
  - SQL
  - 資料庫設計
created_at: 2026-11-16T10:00:00+08:00
updated_at: 2026-11-16T10:30:00+08:00
source_type: manual
---

# 資料庫正規化

## 一、定義

資料庫正規化是透過資料表結構調整，降低資料重複與更新異常的設計方法。

## 二、相關概念

- 第一正規化
- 第二正規化
- 第三正規化

## 相關筆記

- [[資料庫設計]]
- [[SQL 基礎]]
```

### 8.2 知識文章範例

```markdown
---
id: wiki-database-normalization
title: 資料庫正規化
type: wiki
aliases:
  - Normalization
  - Database Normalization
tags:
  - 資料庫
  - SQL
created_at: 2026-11-16T11:00:00+08:00
updated_at: 2026-11-16T11:30:00+08:00
sources:
  - note-20261116-001
---

# 資料庫正規化

## 概念說明

資料庫正規化是...

## 正規化階段

### 第一正規化

...

### 第二正規化

...

### 第三正規化

...

## 相關文章

- [[資料庫設計]]

## 參考來源

- [[資料庫正規化]]（原始筆記）
```

### 8.3 Frontmatter 規範

必要欄位：

| 欄位 | 說明 |
|---|---|
| id | 唯一識別碼 |
| title | 筆記或文章標題 |
| type | `note` 或 `wiki` |
| created_at | 建立時間 |
| updated_at | 最後修改時間 |

選填欄位：

| 欄位 | 說明 |
|---|---|
| category | 分類 |
| tags | 標籤陣列 |
| aliases | 文章別名 |
| source_type | 原始來源類型 |
| sources | 引用的原始筆記 ID |
| summary | 簡短摘要 |

日期應使用 ISO 8601 格式，並保留時區資訊。

## 10. 核心資料模型

第一階段以 IndexedDB 儲存以下資料。

### 10.1 Notes

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | string | 唯一 ID |
| title | string | 標題 |
| content | string | Markdown 正文 |
| categoryId | string / null | 分類 ID |

| isPinned | boolean | 是否釘選 |

### 10.2 WikiArticles

| 欄位 | 型別 | 說明 |
|---|---|---|

### 10.3 Categories

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | string | 唯一 ID |

### 10.4 ActivityLogs

| 欄位 | 型別 | 說明 |
|---|---|---|

## 12. GitHub Pages 部署需求

### 12.1 部署方式

使用 GitHub Actions 自動建置及部署。

基本流程：

```text
本機開發
   |
   v
Git commit / push
   |
   v
GitHub Repository
   |
   v
GitHub Actions
   |
   v
npm install
   |
   v
npm run build
   |
   v
部署 dist/
   |
   v
GitHub Pages
```

### 12.2 部署注意事項

- Vite 的 `base` 路徑必須符合 GitHub Pages Repository 網址。
- 若使用前端路由，必須處理 GitHub Pages 重新整理子路徑時的 404 問題；可使用 Hash Router 或適當的 fallback 方案。
- 部署流程必須能在 GitHub Actions 中成功執行。
- 不可依賴本機才存在的檔案路徑。
- 不可在 Repository 中提交 API Key、密碼或私人筆記。
- 部署後需測試首頁、子頁面、重新整理及靜態資源路徑。

### 12.3 部署驗收

- [ ] GitHub Actions 建置成功
- [ ] GitHub Pages 網站可正常開啟
- [ ] 桌面及手機版布局正常
- [ ] 子頁面可正常瀏覽及重新整理
- [ ] Markdown 編輯、儲存及預覽正常
- [ ] 本機資料不會因一般頁面切換而消失
- [ ] 匯出備份及還原正常

## 13. 開發代理執行指示

請依照本文件逐步開發，不要一次產生大量無法驗證的程式碼。

### 開發規則

1. 開始前先檢查 Repository 現有檔案及技術環境。
2. 若已有專案，優先沿用可用架構，不可任意覆蓋既有功能。
3. 先建立可執行的最小版本，再逐步增加功能。
4. 每完成一個 Phase，先執行建置與必要測試。
5. 不可只製作靜態畫面；按鈕、搜尋、表單及資料操作都必須真正運作。
6. 不可使用寫死的統計數字或假筆記充當正式資料。
7. 若需要示範資料，應提供清楚的「載入範例資料」操作，且允許清除。
8. 優先使用成熟、維護中的套件，不要為簡單功能自行重造複雜工具。
9. 將資料存取、Markdown 處理、搜尋及 UI 元件分層，避免所有邏輯集中在單一檔案。
10. 所有重要操作都要處理錯誤狀態，並向使用者提供明確訊息。
11. 先完成 Phase 1，再依序進行 Phase 2、Phase 3；Phase 4 不可在沒有安全後端的情況下暴露 AI API Key。
12. 每個 Phase 完成後，更新 README，記錄啟動方式、已完成項目及已知限制。

### 第一個開發任務

請先執行以下工作：

1. 檢查目前 Repository 是否已有程式碼。
2. 根據本規格確認技術架構。
3. 建立 React + TypeScript + Vite 專案（若尚未建立）。
4. 建立基本頁面布局、側邊欄及 Dashboard。
5. 完成 Phase 1 的資料模型與 IndexedDB 存取層。
6. 先實作新增、編輯、刪除、搜尋及 Markdown 預覽。
7. 執行建置與測試，修正錯誤後再繼續。

若遇到規格未定義的細節，先選擇最簡單、可維護且符合 GitHub Pages 靜態部署的方案，並在 README 記錄決策，不要自行加入需要付費服務的依賴。
